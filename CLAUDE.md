## Что это за проект

KaLine — интернет-магазин eSIM (Армения, домен kaline.am) плюс услуги
(лаунж-доступ в аэропортах, туры). Три способа взаимодействия с одним и тем
же каталогом и одной базой данных:

1. **Сайт** (`www.kaline.am`) — полноценный e-commerce с регистрацией,
   балансом, промокодами, чатом поддержки, отзывами, реферальной программой.
2. **Telegram-бот** (`@zergsimbot`) — Mini App с тем же функционалом, что и
   сайт (не урезанная версия — специально доводили до паритета, см. ниже).
3. **Админ-панель** — веб-интерфейс для владельца: заказы, каталог, заявки на
   услуги, пользователи, промокоды, статистика.

## Архитектура: три отдельных сервиса на Railway

Это критично понимать — весь класс багов в этом проекте был связан именно с
тем, что это **три независимых развёрнутых контейнера**, не один процесс:

| Сервис на Railway | Что запускает | Команда |
|---|---|---|
| **webapp** | Сайт + Mini App бота + инбокс чата поддержки — всё в ОДНОМ FastAPI-приложении | `uvicorn app.webapp.app:app` |
| **bots** | Оба Telegram-бота (клиентский + поддержки), polling | `python -m app.main` |
| **Admin** | Админ-панель, отдельный FastAPI | `uvicorn app.admin_panel.app:app` |

**У каждого — свой диск.** Файл, сохранённый на диск в одном сервисе,
физически не существует в другом. Это once реально сломало выдачу файлов по
оплаченным заявкам на услуги (админка сохраняла файл на свой диск, сайт/бот
пытались отдать его со своего — 404). Решение: файлы теперь хранятся
**байтами в базе данных** (`ServiceRequest.deliverable_data`,
`ServiceRequestAnswer.answer_file_data` — `LargeBinary`), не на диске. База —
единственный ресурс, реально общий для всех трёх сервисов. См. `docs/DECISIONS.md`.

Все три сервиса подключены к одной Postgres (Railway) через `DATABASE_URL`.

## База данных — ключевые модели

Полный список — `app/database/models.py`. Важное:

- **Двойное владение почти everywhere**: `website_account_id` ИЛИ `user_id` —
  заказ/заявка/избранное/бонус может принадлежать либо аккаунту сайта
  (`WebsiteAccount`), либо пользователю бота (`User`, по `telegram_id`). Это
  заложено с самого начала в `ServiceRequest` — когда добавляли форму заявок
  в бота, миграция базы не понадобилась вообще, просто раньше не было
  бот-стороны роутов.
- **`Package`** — товары eSIM (из esimaccess), `is_regional=True` — региональные
  пакеты (Европа/Азия и т.п., несколько стран в одном).
- **`Product`** + **`ProductQuestion`** — товары лаунж/туры и настраиваемые
  вопросы формы заказа (`TEXT`/`YES_NO`/`FILE`, 3 языка на каждый вопрос).
- **`ServiceRequest`** + **`ServiceRequestAnswer`** — сама заявка на услугу:
  статусы `SUBMITTED → READY → PAID` или `CANCELLED`. `deliverable_data`
  (байты файла от админа) и `answer_file_data` (байты вложения клиента) —
  хранятся в базе, НЕ на диске (см. выше).
- **`RateLimitAttempt`** — БД-backed счётчик неудачных попыток входа и т.п.
  (заменил in-memory реализацию).

Миграции — НЕ Alembic. Смотри `_run_light_migrations()` в `database/db.py`:
на каждый старт делает `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` — идемпотентно,
безопасно гонять на каждом деплое, ничего руками катать не нужно.

## Известные грабли (наступали реально, не гипотетически)

1. **Порядок регистрации роутов в FastAPI решает.** `app.mount("/", StaticFiles(...))`
   перехватывает вообще любой путь, если стоит РАНЬШЕ конкретных `@app.get/@app.post`
   в файле — Starlette матчит по порядку, первый совпавший маршрут побеждает,
   даже если у него не тот метод (тогда просто 405/404, а не "пропускает
   дальше"). Однажды так молча сломались `/api/promo/redeem` и `/api/notifications`
   на несколько дней — были физически недостижимы. Все "перехватчики" (mount,
   catch-all-редиректы) обязаны стоять СТРОГО ПОСЛЕ всех конкретных роутов.
2. **`payments.router` — реально забывали подключить через `include_router()`**
   в `app.py` при рефакторинге. Файл существовал, роуты в нём были правильные,
   но `/api/balance` был 404 в проде до тех пор, пока это не поймали.
3. **CSRF-мидлвар и чтение тела запроса.** Если мидлвар на базе
   `BaseHTTPMiddleware` (то есть `@app.middleware("http")`) читает
   `request.form()`/`request.body()`, тело "съедается" для роута ниже по
   цепочке — FastAPI получит пустые поля формы. Чинится вручную: после чтения
   восстановить `request._receive`, чтобы отдать те же байты повторно (см.
   `app/csrf.py::verify_csrf`).
4. **Порядок `add_middleware()`/`@app.middleware()` относительно `SessionMiddleware`.**
   Мидлвар, зарегистрированный ПОСЛЕ `add_middleware(SessionMiddleware, ...)`
   в файле, физически не может читать `request.session` (AssertionError) — он
   выполняется РАНЬШЕ, чем сессия успевает появиться. Нужно регистрировать
   такие мидлвары (CSRF-проверка) ДО строчки с SessionMiddleware.
5. **Telegram Mini App не умеет нормально скачивать файлы.** Ни `<a download>`,
   ни `tg.openLink()` не гарантируют реального скачивания на устройство —
   максимум откроют файл во внешнем браузере, дальше человек сохраняет
   вручную. Самый надёжный способ отдать файл клиенту из бота — обычным
   сообщением (`send_photo`/`send_document` через `aiogram.types.BufferedInputFile`,
   см. `products.py::pay_service_request`), а не через ссылку в Mini App.
6. **CSS-классы `.qa-purple/.qa-blue/.qa-orange/.qa-green`** (иконки в боте) —
   названия НЕ соответствуют реальным цветам (`.qa-green` красит в оранжевый).
   Разбираться при добавлении новых иконок — либо сверяться с реальным цветом
   в CSS, либо использовать `.row-icon` (всегда зелёный, для списков).
7. **`[hidden]` атрибут проигрывает явному `display` в классе** — если
   элемент скрывается через `el.hidden = true`, а у него в CSS есть класс с
   `display: flex/block`, атрибут `hidden` не сработает без явного
   `.class[hidden] { display: none !important; }`.

## Безопасность — что уже сделано

- **CSRF**: токен в сессии + скрытое поле формы, проверка в мидлваре
  (`app/csrf.py`). Применяется к сайту (`/shop/*`) и ко всей админке. НЕ
  применяется к `/api/*` (бот) и `/support-chat/*` — там авторизация через
  подписанные Telegram initData, подделать с чужого сайта нельзя в принципе.
- **Rate limiting**: БД-backed (`RateLimitAttempt`), переживает рестарт
  процесса и общий для всех реплик — раньше был in-memory dict, сбрасывался
  при каждом деплое.
- **Пароли**: хешируются, нигде не хранятся открытым текстом.
- **Файлы**: тип и размер загрузки проверяются (`uploads.py`).
- **robots.txt / sitemap.xml / meta description**: есть (`shop.py`).

Не сделано / осознанно отложено — см. `docs/DECISIONS.md` и раздел ниже.

## Платежи — статус на момент написания

Провайдеры: **Idram** (карты, AMD), **OxaPay** (крипта, любой адрес),
**Wallet Pay** (Telegram-кошелёк), **Stripe** (только пополнение баланса на
сайте, не прямая оплата заказа). Плюс тестовый режим.

**`ENABLE_TEST_PAYMENT`** — если `true`, кнопка "тестовая оплата" сразу метит
заказ оплаченным и реально дёргает esimaccess (выдаёт настоящий eSIM
бесплатно). Must be `false` в проде — обязательно проверить перед реальным
запуском, см. `docs/DEPLOYMENT.md`.

  в `index.html`/`base.html`, иначе браузер/Telegram отдаёт из кэша старое.

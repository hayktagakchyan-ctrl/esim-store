# Техническое задание: Telegram-бот для продажи eSIM (notebookcentre / eSIM Access)

## 1. Суть проекта

Клиент покупает через Telegram-бота eSIM с интернетом (данные предоставляет
B2B-провайдер **esimaccess.com**, к которому мы подключаемся как реселлер).
Заказчик (владелец) администрирует заказы через отдельную веб-панель и отвечает
на вопросы клиентов через отдельного приватного бота — без раскрытия личного аккаунта.

Стек: **Python, aiogram 3.x, SQLAlchemy (async), FastAPI**. Готовый рабочий
скелет с этой архитектурой уже приложен (папка `esim_bot_project/`) — в нём
реализована структура, БД, все хендлеры и вся логика роутинга; недостающие
части помечены `TODO` и перечислены в README проекта.

## 2. Три компонента системы

### 2.1 Клиентский бот (публичный)
Единственная точка контакта с покупателем.

- **/start** → главное меню: «Купить eSIM», «Мои eSIM», «Поддержка».
- **Каталог** → выбор страны → список пакетов (объём данных / срок / цена) → подтверждение → оплата → выдача eSIM.
- **Выдача eSIM** — после оплаты бот показывает QR-код/данные активации и текстовую инструкцию, полученные от esimaccess.
- **Мои eSIM** — список купленных eSIM с текущим статусом; по запросу — актуальный остаток трафика (живой запрос к esimaccess, не из кэша).
- **Поддержка** — кнопка, после которой следующее сообщение клиента уходит в приватный чат поддержки (см. 2.2), а ответ администратора приходит клиенту в этот же чат.

### 2.2 Бот поддержки (приватный)
- Отдельный Telegram-бот, отдельный токен. Знает только один чат — личный чат администратора.
- Присылает туда вопросы клиентов (с именем/username/telegram_id, но без раскрытия его самого клиенту).
- Администратор отвечает **реплаем** на сообщение с вопросом → ответ автоматически уходит нужному клиенту в клиентский бот.
- Если кто-то посторонний напишет боту поддержки напрямую — бот полностью игнорирует (не должен подтверждать своё существование/назначение).
- Вся переписка логируется в БД (таблица `support_messages`) для истории.

### 2.3 Админ-панель (веб, только для владельца)
- Обязательный функционал: **просмотр всех заказов** (с фильтром по статусу) и **оформление возврата**.
- Простая авторизация логин/пароль (однопользовательская, без ролей).
- Карточка заказа: клиент, пакет, цена, ID заказа у esimaccess, ICCID, статус, история.
- Кнопка «Оформить возврат» → меняет статус заказа и фиксирует причину. Фактический возврат денег зависит от платёжного провайдера (см. п.4.3) и в первой версии оформляется вручную в кабинете провайдера — сюда провести автоматизацию можно будет позже.

## 3. Данные и статусы заказа

Статусы заказа: `pending_payment → paid → provisioning → active`, либо `failed` /
`refunded` на любом этапе после оплаты. Полная схема таблиц — в
`app/database/models.py` готового скелета (`users`, `packages`, `orders`,
`support_threads`, `support_messages`).

## 4. Интеграции — что нужно доделать

### 4.1 esimaccess.com API
Интерфейс уже описан в `app/services/esimaccess.py` (методы `list_packages`,
`create_order`, `query_order`, `get_esim_usage`) — вся остальная система вызывает
только эти методы и не знает деталей API. Разработчику нужно:

1. Открыть `docs.esimaccess.com`, разделы **Authentication** и примеры запросов
   на список пакетов / создание заказа / проверку статуса / остаток трафика.
2. Подставить реальный `base_url`, реальный способ авторизации (заголовок или
   Bearer-токен) и реальные названия полей запроса/ответа.
3. Проверить формат обёртки ответа (успех/ошибка) и поправить `_post()`.

Заказчик пришлёт доступ к личному кабинету esimaccess (там же выдаются ключи API).

### 4.2 Синхронизация каталога
Периодическая задача (по крону или APScheduler), которая тянет актуальный список
пакетов из esimaccess и обновляет таблицу `packages`, применяя наценку заказчика.
Наценка — фиксированный процент или таблица правил по стране/объёму, уточняется
у заказчика отдельно.

### 4.3 Оплата
Провайдер оплаты **пока не выбран** заказчиком — будет сообщён дополнительно
(варианты: Telegram Payments, ЮKassa/другой локальный эквайринг, приём в крипте).
Место интеграции уже размечено в `app/client_bot/handlers/order.py`. Общий контракт
для любого варианта: получить подтверждение оплаты → перевести заказ в `paid` →
вызвать `create_order` у esimaccess → сохранить `iccid`/QR → перевести в `active`.

## 5. Нефункциональные требования

- Токены ботов, ключи esimaccess, пароль админки — только в `.env`, не в коде и не в git.
- Логирование ошибок при обращении к esimaccess (сеть/бизнес-ошибки) — не ронять бота,
  показывать клиенту понятное сообщение («не получилось оформить заказ, служба поддержки уже уведомлена» и т.п.), а техническую ошибку — в лог.
- База — Postgres в проде (в скелете по умолчанию SQLite для локальной разработки, меняется одной строкой в `.env`).
- Все три процесса (клиентский бот, бот поддержки, админка) должны автоматически перезапускаться при падении (systemd/supervisor/Docker — на усмотрение разработчика).

## 6. Критерии приёмки

- [ ] Клиент может пройти путь от `/start` до получения QR-кода eSIM после оплаты.
- [ ] Клиент может посмотреть список своих заказов и текущий остаток трафика.
- [ ] Вопрос через кнопку «Поддержка» приходит администратору в отдельный бот; ответ реплаем доходит клиенту; посторонний в боте поддержки не получает ответа.
- [ ] В админ-панели виден полный список заказов с фильтром по статусу, и по любому заказу можно оформить возврат.
- [ ] Все секреты — в `.env`, отсутствуют в коде и в истории git.

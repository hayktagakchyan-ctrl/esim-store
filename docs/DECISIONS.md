# DECISIONS.md — почему сделано именно так

Не хронология изменений — конкретные развилки, где было больше одного
разумного варианта, и почему выбрали этот. Полезно перед тем, как "улучшать"
что-то из списка ниже не глядя.

## Файлы заявок на услуги — в базе, не на диске

**Развилка**: где хранить файл (ваучер от админа, скан билета от клиента) —
на диске сервиса, в объектном хранилище (S3/R2), или байтами в Postgres.

**Почему не диск**: три сервиса Railway — три независимых контейнера с
разными дисками. Файл, сохранённый через админку, физически не существовал
на диске у webapp (который его и должен был отдавать клиенту) — 404 при любой
попытке открыть. Поймали это на реальном тесте, не в теории.

**Почему не S3/R2 (пока)**: это правильное долгосрочное решение, но требует
новой инфраструктуры (аккаунт, ключи, ещё одна точка отказа) ради файлов,
которые по факту небольшие (ваучеры/сканы документов, не видео). Postgres
уже общий для всех трёх сервисов — использовать его как хранилище для
маленьких файлов дало рабочее решение без единой новой зависимости.

**Если объём вырастет** (много крупных файлов) — тогда да, стоит пересмотреть
в сторону объектного хранилища. Сейчас это осознанно отложенный, а не
забытый вопрос.

## Email — Resend HTTP API, не SMTP

Railway (и многие облачные хостинги) либо блокируют исходящий SMTP на 587
порту, либо он там нестабилен — в логах это выглядело как
`Network is unreachable`/таймауты. HTTP на 443 порту так не блокируют. Resend
выбран как конкретный сервис — есть щедрый бесплатный тариф и работает по
HTTP.

## Rate limiting — в базе данных, не in-memory

Изначально было — простой dict в памяти процесса. Проблема: перезапуск
сервиса (обычное дело при каждом деплое) полностью обнулял счётчик неудачных
попыток входа. Плюс если Railway когда-нибудь поднимет вторую реплику того же
сервиса — у каждой была бы своя память, счётчик не был бы общим. Переехали на
таблицу `RateLimitAttempt` в той же Postgres — она и так общая для всех трёх
сервисов.

Осознанный компромисс: это НЕ защита от распределённого перебора (ботнет с
тысячи IP всё ещё может пытаться) — цель была просто не дать перебирать
пароль в лоб простым скриптом. Для полноценной защиты нужен Redis с более
умной логикой (sliding window и т.п.) — не делали, потому что это другой
масштаб проблемы, чем реально стоял.

## CSRF — токен в сессии, не double-submit cookie

Стандартный synchronizer token pattern: токен генерируется один раз на
сессию, кладётся в подписанную (Starlette сама подписывает) cookie сессии и
дублируется в скрытое поле формы. Проверка — совпадение.

Специально НЕ распространяется на `/api/*` (бот) и `/support-chat/*` — там
авторизация в принципе не через cookie, а через подписанные Telegram
initData, которые сторонний сайт не может подделать (в отличие от cookie,
которая браузер сам подставит куда угодно). Навешивать CSRF-токены поверх
этого было бы избыточно и просто сломало бы мини-апп без реальной пользы.

## Шрифт для армянского — самостоятельно на сервере, не Google Fonts CDN

Сначала были на Google Fonts CDN (Unbounded/Geist/Noto Sans Armenian).
Убрали ради приватности — загрузка шрифта с fonts.googleapis.com передаёт IP
посетителя Google без его согласия, это конкретный, не гипотетический риск
по GDPR (в Германии по этому поводу были реальные судебные иски владельцам
сайтов). Перешли на системные шрифты ОС.

Проблема: системный шрифт не у всех устройств прилично рисует армянские
буквы — конкретно словосочетание "-ից" ("от") в интерфейсе превращалось в
нечитаемую кашу, похожую на "-hg". Финальное решение — вернуть Noto Sans
Armenian, но не через Google CDN, а файлом (`.woff2`, лицензия OFL, свободно
распространяется) прямо со своего сервера — `/shop-static/fonts/` и
`/fonts/` (сайт и бот отдельно). Так и приватность не страдает (запрос идёт к
своему серверу), и армянский текст рисуется правильно. Только сам армянский
диапазон (`unicode-range: U+0530-058F, U+FB13-FB17`) — латиницу по-прежнему
закрывают системные шрифты, лишний вес не тянем.

## Форма заявок на услуги вместо "спросить в чате"

Изначально (и в исходном README/TZ) лаунж/туры оформлялись только через чат
с поддержкой — без цены, без структурированных данных. Заменили на форму с
настраиваемыми вопросами (`ProductQuestion`: текст/да-нет/файл, на 3 языках)
+ статусный флоу (`SUBMITTED → READY → PAID/CANCELLED`) + оплата с
внутреннего баланса. Чат никуда не делся, но перестал быть единственным
способом — теперь это структурированная заявка, которую админ обрабатывает
предсказуемо (видит все ответы сразу, а не выцарапывает детали из переписки).

Изначально форму сделали только для сайта — бот-сторону дособрали позже
отдельным заходом. База была спроектирована сразу под обоих владельцев
(`website_account_id` ИЛИ `user_id` у `ServiceRequest`), поэтому миграция при
добавлении бот-стороны не понадобилась вообще, только сами роуты и интерфейс.

## Возврат — автоматический только для оплаты с баланса

Когда админ отклоняет/возвращает заявку или заказ, автоматическое зачисление
обратно клиенту работает ТОЛЬКО если оплата была с внутреннего баланса — в
этом случае деньги никуда не уходили от нас, возврат это просто обратная
проводка внутри своей же базы, без внешних рисков.

Для Idram/OxaPay/Wallet Pay/Stripe — возврат остался ручным (админ делает его
в личном кабинете провайдера). Осознанно не стали писать код, вызывающий
API возврата этих провайдеров вслепую — ни для одного из них не было
подтверждённой документацией однозначной точки входа именно для возврата
конкретного платежа, а гадать с реальными деньгами клиентов — плохая идея.
Если у какого-то из провайдеров появится подтверждённый эндпоинт возврата —
это лёгкое расширение `admin_panel/app.py::refund_order`, структура уже
предусматривает разные ветки по `payment.provider`.

## "Регион" — отдельный экран в боте, не фильтр внутри общего списка

Изначально регионы (Европа/Азия и т.п.) были просто ещё одним значением
фильтра-пилюли рядом с "Все"/"Избранное" на общем экране стран. Переделали в
отдельный экран со своим полем поиска — регионы концептуально другая вещь
(несколько стран в одном пакете), и смешивание в одном списке с фильтром
делало это малозаметным для пользователя. Кнопка-вход на новый экран
использует `.row-icon` (не `.quick-action-icon`) специально из-за путаницы
с цветами классов `.qa-*` — см. CLAUDE.md, раздел "известные грабли".
